Connection help
  1. Keep runtime-database.html, runtime-database.js and runtime-database.css together on your separate static frontend.
  2. The backend address is set in RUNTIME_BACKEND_URL inside runtime-database.js. Hosted pages and local previews both use that address; there is no automatic switch to localhost.
  3. Deploy the backend's runtime status API. No token, frontend proxy or PostgreSQL connection is required.
  4. Check the backend runtime status service. It must return runtime JSON rather than HTML or a 404.
Runtime scope and retention rules

Counts reset on backend restart and cover this instance's observed, unexpired Quick User activity, not all database users or currently online people. The ordinary application can observe retained users when they return; this viewer does not query PostgreSQL. Memberships, subscriptions, payments, contact details, conversations and credentials are excluded.

For subscriber identification and payment reconciliation, use the separate owner subscriber/payment database viewer. It requires owner authorization and reads PostgreSQL through the backend; its records are not added to this public runtime API.

Free activity lasts at most three days. After the fifth free buyer or seller lead, the response window ends after 24 hours or at the original deadline, whichever comes first. Search and refresh never extend retention. Diagnostic records are cleared no later than 72 hours after their creation timestamp. Displayed lead counts are observed matches, not a replacement for the application's authoritative quota checks.

The read-only status endpoint is intentionally accessible without a token. It uses anonymous references rather than publishing login usernames. Existing account and conversation access rules are unchanged.
